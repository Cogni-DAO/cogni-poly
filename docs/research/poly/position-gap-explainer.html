position_gap in five minutes

How the policy works · the data model it reads · the math (it’s mostly math) · where branching still exists. §9 is the live cost-of-skip data — jump there if you only want the next move.

1. The shape of the problem

Legacy target_percentile_scaled sizes each fill in isolation. When target’s position is lopsided, the per-fill view inverts — we end up over-weighted on the side target barely cares about.

swisstony ATP Sinner/Ruud, 2026-05-17:

Target's actual position
99.5% Sinner.
Our mirror (legacy)
28% Sinner72% Ruud

Our Ruud VWAP ended up 5.75× target’s. The bug is structural — per-fill sizing has no concept of “target’s current state vs ours.”

2. The whole policy, in five lines

position_gap sizes from desired position minus actual position, not from the fill notional. Every fill becomes a re-evaluation trigger, not a sizing input.

desired_shares = target_shares[token]  ×  target_scale     # per-target knob, e.g. 0.0001
gap_shares     = desired_shares  −  our_shares[token]
gap_usdc       = gap_shares  ×  fill.price
                 ↓ clamp to market floors & per-leg cap
intent_usdc

The four inputs are already in the planner’s hands at fill time. No new tables, no new RPC, no new ports.

3. Logic vs math: where does branching live?

Inside the policy itself: almost no branching. Just four short-circuit guards on the math. Skip-reason precedence top-to-bottom; first hit wins:

if  tokenId is missing on the fill        → skip  below_market_min
if  gap_shares  ≤ 0                       → skip  followup_not_needed
if  gap_usdc    < min_usdc_notional       → skip  below_market_min
   sized = clamp_to_market_floors(gap_usdc)
if  cumulative_intent + sized > cap        → skip  position_cap_reached
else                                       → PLACE

No discriminated routing, no per-side cases, no “is this a layer or a hedge?” question. Just one inequality at each step.

The legacy layer / hedge branches at the outer dispatch (decideMirrorBranch) are short-circuited when the policy kind is position_gap — every fill lands as new_entry and the gap math handles same-token follow-ups naturally (the gap shrinks as our position grows).

4. The full planner flow it sits in

The policy is the sizing step. The gates ahead of it still run, and that’s where the actual decision-tree branching lives:

already_placed              ← idempotency on (target_id, fill_id)
market_past_end_date        ← market resolved before plan-time
price_outside_clob_bounds   ← tick-grid rejection
target_dominant_other_side  ← bug.5048 dominance gate (cost-fraction)
vwap_floor_breach           ← bug.5048 VWAP gate                 see §6
position_gap sizing         ← policy lives here          see §3
PLACE                       → intent → authorizeIntent (tenant cap)

Each gate is a single boolean. They’re shared across all sizing policies — Phase 4’s GapExecutor dissolves several of them by moving their semantics into the gap order itself (price-limit ceiling instead of a per-fill VWAP gate, etc.).

5. The data model the planner reads

One snapshot per fill. Four fields out of the bundle drive position_gap:

Note: our_vwap_usdc exists on the cache view but position_gap doesn’t consult it. See §6.

6. VWAP — should be first-class on BOTH sides; today it isn’t

Why isn’t VWAP first-class for both target wallets and our wallets?
You’re right that it should be. Today it isn’t — that’s a real design gap. Phase 2 reads target VWAP as a derived quantity per-fill and ignores our own VWAP entirely. Phase 3+ promotes it to a stored field on both sides. Specifics below.

Re-derived every fill. Read only by the upstream vwap_floor_breach gate (skips fills above this + tolerance). Not consulted by the gap math itself.

Cost-basis-on-residual caveat: target_vwap_for_token derives from currently-held shares only. Pre-Phase-4 patch that keeps position_gap intellectually honest

Until Phase 3 ships, we can still promote VWAP discipline to the order rather than skipping per-fill. The diff is small:

# Under position_gap only, in applyPositionGapSizing:
target_vwap = sum(t.cost_usdc) / sum(t.size_shares)   # same derivation
vwap_ceiling = target_vwap + vwap_tolerance
intent.limit_price = min(fill.price, vwap_ceiling)   # NEW: cap at ceiling
drop vwap_floor_breach skip for this policy          # gate becomes property of order

This is the Phase-4 mechanism, backported to one policy. Without Phase 3, target_vwap is still residual-cost-basis (the cost-basis-on-residual caveat above). With Phase 3, it becomes chain-truth running VWAP — same code path, better data.

7. Hedges — no special case

Do we factor in entry points of hedges?
No, and we don’t need to. Each token_id on a market gets its own independent desired_shares. The “hedge” side of a binary is just another token; we size to its gap the same way.

Concrete: target holds Sinner and Ruud, so there are two entries in state.target_position.tokens[]. Two fills arriving on different tokens compute two unrelated gaps:

// Sinner fill
desired = 88,931 × 1e-4 = 8.89        gap = 8.89 - our_sinner

// Ruud fill (totally independent)
desired = 14,925 × 1e-4 = 1.49        gap = 1.49 - our_ruud

The legacy position_followup machinery (min_target_hedge_ratio, min_target_hedge_usdc, max_hedge_fraction_of_position, etc.) is bypassed when policy.kind === "position_gap". Each gap stands alone.

Honest gotcha: the current applyPositionGapSizing reads our_qty_shares only if state.position.our_token_id === fill_token_id. If the fill arrives on the other leg we hold (opposite_token_id), we’d see our_shares = 0 for that token and over-state the gap by exactly opposite_qty_shares. Not currently a real-world bug (we rarely hold both legs under the dominance gate) but worth knowing — trivially fixable when it matters.

8. Neg-risk — invisible to the planner

Do we factor in neg-risk?
No. The planner doesn’t know which markets are neg-risk. It’s a per-market routing flag the CLOB adapter looks up at order-signing time.

Same OrderIntent shape goes out of the planner regardless. The Polymarket adapter (polymarket.clob.adapter.ts) calls getMarketConstraints(tokenId) and gets back { tickSize, negRisk, feeRateBps }, then routes the signed order to the right exchange contract (regular vs. neg-risk). Neg-risk markets:

  • need setApprovalForAll on a different CTF exchange address (handled at wallet provisioning, not at fill time);
  • carry different fee math (also adapter-side);
  • have the same on-chain settlement vocabulary so the position snapshot looks identical to the planner.

If neg-risk ever needs to influence sizing (it doesn’t today), the seam is to add a field on MarketConstraints and read it in the planner — not to add it to SizingPolicy.

10. Policy knobs — mapping from the legacy UI to position_gap

The existing per-target card in the UI exposes three knobs (image: swisstony card with THRESHOLD P80 slider, P100 MAX = $15.00, active toggle). The direct mapping to position_gap:

Legacy UI knobDB columnRole under target_percentile_scaled (TPS)Role under position_gap
Active toggle disabled_at NULL/timestamp same — soft-delete same — soft-delete
P80 / P100 Threshold slider mirror_filter_percentile Load-bearing. Below this target-position percentile, fills skip below_target_percentile. Drives the per-fill conviction filter. Mostly inert. position_gap has no per-fill percentile filter; the conviction knob is target_scale, not pXX. Still present on the row (the schema didn't drop it) but unread by the gap path.
P100 MAX = $15 mirror_max_usdc_per_trade Per-fill notional cap. p100 fills map to this; smaller fills scale linearly to market floor. Same field, same name, same role. Per-leg cap on gap_usdc. Phase 2 keeps this verbatim.
(missing) target_scale (NEW — not yet a column) n/a The conviction knob. Fraction of target's per-token shares we aim to hold. Today hard-coded to 1e-4 in DEFAULT_POSITION_GAP_TARGET_SCALE — same for every target.
(missing) vwap_tolerance (currently a constant) Per-fill vwap_floor_breach tolerance (default 0.005) Same default; under position_gap it would become the order's limit_price ceiling once the §6 patch lands.

Conceptual answer

We must have pXX understanding + user max bet, right?
Max bet: yes — same field (mirror_max_usdc_per_trade), same UI input, same role as the per-leg gap cap. pXX: no, not for position_gap. The percentile concept comes from the per-fill view ("only mirror fills above target's pXX position size"). position_gap doesn't decide per-fill — it decides per-position-state. The analogous conviction knob is target_scale: "what fraction of target's per-token shares do I want to hold?"

So the user-facing translation is:

# Legacy TPS UI:
"Mirror fills above swisstony’s p80 token positions, up to $15."
  → mirror_filter_percentile = 80
  → mirror_max_usdc_per_trade = 15

# Equivalent position_gap UI (proposed):
"Hold 0.5% of swisstony’s per-token shares, up to $15 per leg."
  → target_scale              = 0.005
  → mirror_max_usdc_per_trade = 15

Same shape of intent. Different shape of math. The pXX slider in the existing card has no meaningful semantic under position_gap and could be hidden / repurposed as a target_scale slider when this policy is selected. Until the schema column for target_scale lands (proposed Phase 2 cleanup PR), the only way to tune it is editing DEFAULT_POSITION_GAP_TARGET_SCALE in the bootstrap.

11. Turning it on

curl -X PATCH https://poly.cognidao.org/api/v1/poly/copy-trade/targets/<id> \
     -H "Authorization: Bearer $KEY" -H "content-type: application/json" \
     -d '{"sizing_policy_kind":"position_gap",
          "mirror_filter_percentile":80,
          "mirror_max_usdc_per_trade":15}'

Per-target opt-in. Legacy targets keep target_percentile_scaled by construction. target_scale currently lives behind a bootstrap constant (1e-4) — per-target tunability via the API is a follow-up.

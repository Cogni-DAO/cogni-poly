# Δ-Minimizer

We copy-trade ONE target wallet at a time (today: `swisstony`). Every divergence is a bug worth understanding. The algorithm has known fundamental issues catalogued in `work/charters/POLY_COPY_DELTA.md`. Your job: investigate one market, produce one high-confidence finding, map it to a charter class (or argue for a new one and update the charter), drop the fluff.

## The workflow (4 steps, in order)

### 1 · Run the tool

```bash
pnpm tsx scripts/delta-minimizer.ts '<input>'
```

Accepts: event slug (`lal-bet-elc-2026-05-12`), conditionId (`0xb974…`), comma-separated conditionIds, or fuzzy event-title text. Produces a timestamped subdir at `research/delta-minimizing/<slug>-<iso>/` containing:

- `report.html` — human-facing report. KPIs, per-market positions table (with VWAP-delta highlights), per-market timeline charts (log-$ Y-axis, VWAP overlay, decision-marker strip). Has a placeholder `<!-- TAKEAWAY -->` block at the top — that's where YOU author.
- `bundle.json` — structured data: groups, metrics, decisions, placedOrders, auto-scored causes. This is your read surface.
- `ai-walkthrough.md` — verbose data-source notes, computation math, code-path map. Useful for the next agent who picks up this incident.

A shared `research/delta-minimizing/charter.html` is re-rendered every run. Reports are tracked in git (history is essential).

### 2 · Cross-reference code BEFORE claiming anything

**Mandatory reads to ground a finding**:

- `nodes/poly/app/src/features/copy-trade/plan-mirror.ts` — every skip reason in `bundle.json/decisions` corresponds to a specific code path here. Quote the line number when you cite it. Example: `followup_position_too_small` at `plan-mirror.ts:563` — gate fires when our mirror exposure < `min_mirror_position_usdc`. Don't say "likely" — say what the code does.
- `nodes/poly/app/src/features/copy-trade/types.ts` — `MirrorReason` enum + intent schema.
- `nodes/poly/app/src/features/wallet-analysis/server/market-exposure-service.ts` — the dashboard math the tool mirrors. Read this if numbers ever disagree with the UI.
- `work/charters/POLY_COPY_DELTA.md` — the existing D1–D8 classes. If your finding doesn't fit one of them, either argue for an extension OR explicitly note "no clean charter row".

**Bundle data → code mapping cheat-sheet** (verified, not guesses):

| Skip reason                   | Code                                                           | What it actually means                                                                                                                                                                         |
| ----------------------------- | -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `below_target_percentile`     | `plan-mirror.ts:92–115`                                        | Target's _cumulative_ token cost < `min_target_usdc` (`target_percentile_scaled` policy uses `targetSizingUsdcForFill:657–666` which returns `targetTokenCostUsdc`, NOT triggering fill size). |
| `vwap_floor_breach`           | `targetVwapForToken` + `NEVER_PAY_ABOVE_TARGET_VWAP` invariant | Triggering fill price > target's running VWAP + tolerance.                                                                                                                                     |
| `target_dominant_other_side`  | `analyzeTargetDominance` + `decideMirrorBranch`                | Target's cost-basis fraction on this token < `min_target_side_fraction` (default 0.2).                                                                                                         |
| `followup_position_too_small` | `plan-mirror.ts:563, 572, 609, 618`                            | OUR mirror exposure < `min_mirror_position_usdc`. After first micro-entry, this fires on every subsequent followup attempt.                                                                    |
| `position_cap_reached`        | `applyMarketFloors`                                            | Cumulative intent + new size > `max_usdc_per_trade`.                                                                                                                                           |
| `already_resting`             | branch evaluation                                              | We already have a resting order on the same token.                                                                                                                                             |

### 3 · Iterate the takeaway VISIBLY (5 drafts minimum)

The takeaway is YOUR work product, not the script's. The script's auto-scored Δ-causes are removed from the human report on purpose — they're algorithmic, not analytical. Write a takeaway by:

1. **Draft v1** in your response. Plain text. State what you see.
2. **Critique v1** in your response. What's vague? What's "likely" / "probably" / unverified?
3. **Draft v2**, **critique v2**, **draft v3**, … through at least v4.
4. Show ALL drafts in the chat so the user can see your reasoning. Hiding the iteration defeats the purpose.
5. **Inject final** (v5) into the HTML between `<!-- TAKEAWAY:START -->` and `<!-- TAKEAWAY:END -->` markers as a `<table class="findings">` with columns `# · Finding · Charter · Confidence`, followed by a `<div class="fix">` block.

**Discipline on findings**:

- Each finding has a **% confidence** (mandatory). Cite the evidence that earns each percentage point. 95% means "code path read + decision count verified + chart confirms". 70% means "data points in this direction but the causal chain is plausible-not-proven".
- Each finding maps to a **charter class** (D1–D8) OR explicitly says "no clean row (new symptom)" — don't invent a class without updating the charter file. If you do propose a new class, write the charter row in the same turn.
- Findings must cite a code line. "Downstream of `<gate>`" is not enough — name the file and line that fires that gate.
- Findings must be ROOT cause, not symptom. Example: "VWAP delta" is a SYMPTOM of "single-fill per side" (D6), not its own class.
- Headline metrics (e.g. "+20.7%") that look favorable need a variance/luck check. If the return depends on a single fill's timing, say so.

### 4 · Pareto fix block (one line, actionable)

Below the findings table, one **Fix** line:

- ONE highest-leverage immediate code change with a file-or-config target.
- Plus: "Long-term: D2 position-mirror refactor dissolves both" (if applicable).
- If the fix would falsify a positive-looking headline (e.g. "+20.7% is variance, proper sizing would be breakeven"), include that as the second sentence in the Fix block.

## What the tool DOES (so you know what NOT to redo)

- Resolves the input to conditionIds via `poly_market_metadata` (prefix-match on event_slug — catches `<slug>` and `<slug>-more-markets` siblings).
- Auto-detects the single copy-target from `poly_copy_trade_decisions` (the wallet with the most decisions on those markets).
- Anchors on our wallet's positions (`OUR_POSITIONS_ANCHOR_GROUPS` invariant from `market-exposure-service.ts`). If we never held the market, the tool exits with a message.
- Pulls OUR legs from `poly_trader_position_snapshots` (NOT `current_positions` — that filters `active=true` which drops losers; for Δ-analysis we need every leg).
- Pulls target legs from `poly_trader_position_snapshots` (latest per (cond, token), survives target redeem).
- Cost basis denominator = `max(rollup_buy_notional, snapshot_cost)` per (wallet, condition), matching dashboard's `aggregateWalletReturn`.
- Δ-investigation value override: `outcome=loser → value 0`; winners keep snapshot value (we do NOT zero redeemed winners — dashboard does that to avoid USDC double-counting, but we need realized P/L visible on the position).
- Chart x-axis: first activity → last activity (NOT market resolution — keeps action visible).
- Chart y-axis: log-$ cost basis. VWAP overlay on right $-axis. Decision markers below, dimmed if hedge-side.
- Group by `event_slug`. Each group gets its own 3-KPI band (Our / Target / Δ-vs-target), per-market table, and chart.

## What the tool does NOT do

- It does NOT author findings, charter assignments, or confidence levels. Those are YOUR job.
- It does NOT touch Loki. If a decision row has `outcome='error'`, the errorCode lives on the pino log line. Add a Loki step to your investigation if needed: `scripts/loki-query.sh '{env="production",service="app"} | json | component="mirror-pipeline" |~ "<fill_id_prefix>"' 1440 200`.
- It does NOT update `POLY_COPY_DELTA.md`. If you discover a class that isn't covered, edit the charter in the same turn — don't just claim it.

## Common failures (read once)

- **Claiming a new charter class without verifying the symptom isn't already covered.** D6 ("Per-fill sizing instead of per-gap sizing") already covers `followup_position_too_small`. Read the existing rows first.
- **Saying "likely" or "probably" instead of citing code.** If you haven't read the file, don't write the finding.
- **Hiding the iteration.** The user wants to see drafts v1→v5 in chat. Don't skip to "here's the final".
- **Defaulting to the auto-scored top class.** The script's classifier is a starting heuristic. Read the decision timeline; the dominant pattern by _count_ isn't always the _root_ cause.
- **Treating a symptom as the root cause.** "VWAP delta" / "value zero" / "won by accident" are observations. Trace each one back to a single code path.
